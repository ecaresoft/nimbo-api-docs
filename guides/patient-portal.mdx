---
title: "Build a patient portal"
description: "Verify a phone number and read records for people authorized by a patient portal session."
---

Patient portal authentication is separate from integration OAuth. Use the API host approved for your integration and an approved test phone for verification. All paths below are relative to `NIMBO_API_BASE_URL`, including `/api/v1`.

## Request and validate a code

Send [`POST /patient_portal/auth`](/api-reference/patient-portal-authentication/request-a-patient-portal-otp) with the phone’s country calling code and number. If your client supports both four- and six-digit codes, send `supports_six_digit_otp` as a JSON boolean on the initial request and on resends. Replace the placeholders with your approved test phone details.

```json
{
  "country_code": "<COUNTRY_CALLING_CODE>",
  "phone": "<TEST_PHONE>",
  "supports_six_digit_otp": true
}
```

Use `code_length` from the HTTP 200 JSON response to configure code entry. It can be `4` or `6`. Treat an empty HTTP 200 as a four-digit challenge. Clients that omit the opt-in receive an empty response and continue using four digits. After a successful resend, use the latest code and its reported length.

Collect the code received by the patient, then send [`POST /patient_portal/validate`](/api-reference/patient-portal-authentication/validate-a-patient-portal-otp) with the same phone details. Keep `code` as a string so leading zeros are preserved.

```json
{
  "country_code": "<COUNTRY_CALLING_CODE>",
  "phone": "<TEST_PHONE>",
  "code": "<ONE_TIME_CODE>"
}
```

The successful validation response contains `token`. Keep it private and use it as the bearer token on patient-portal reads. Do not substitute an integration OAuth token or assume the portal token supports OAuth refresh.

## Select an authorized person

Call `GET /patient_portal/people` with `Authorization: Bearer <PATIENT_PORTAL_TOKEN>`. A phone can be linked to multiple patient identities. Let the patient select the appropriate returned person and use that person's ID in subsequent requests; do not assume that any known patient ID is authorized.

## Retrieve records and booking links

| Need | Path after `/patient_portal/people/{person_id}` |
| --- | --- |
| Organization profile | `/organization` |
| Clinical visits | `/consultations` |
| Files, lab tests, prescriptions | `/attachments`, `/lab_tests`, `/prescriptions` |
| Vital-sign summary and medical history | `/vital_signs`, `/medical_history` |
| Individual vital-sign captures | `/vital_signs_history` |
| Appointments and requests | `/consultation_schedules`, `/consultation_requests` |
| Available booking portals | `/organization_portals` |

Check each response schema for its JSON envelope. Booking links depend on the organization’s subscription and visibility settings.

### Show a visit and its location

Use `GET /patient_portal/people/{person_id}/consultations` for visit summaries. Pass the selected consultation ID to `GET /patient_portal/consultations/{id}` for detail. The list accepts `page` and `per_page`, defaults to 10 results per page, and caps page size at 100.

Use `appointment.starts_at` for the scheduled time when `appointment` is present. The top-level `starts_at` is the clinical start time. Add `include=encounter` to either read when you also need the nullable `encounter_id`.

Organization and location reflect the recorded branch, including inactive branches. Missing or deleted context returns null. Visit detail shows the branch’s current address and contact information. Preserve stored names and empty values when displaying the branch. `organization_name` still identifies the physician account’s organization. Inactive physicians remain in visit history with `doctor_active: false` and `url_portal: null`.

### Load appointment history

Send `scope=history` to list past and future appointments, newest first, including eligible deleted appointments with accepted cancellation requests.

```http
GET /api/v1/patient_portal/people/2001/consultation_schedules?scope=history&page=1&per_page=20
Authorization: Bearer <PATIENT_PORTAL_TOKEN>
```

Omit `scope` for the default recent and upcoming schedule list. Load its pages separately from history. Both modes default to 10 results per page and cap page size at 100.

Use `consultation_id` from history to open the clinical visit. Read `consultation_finished_at` to tell whether a started consultation has finished. Read `arrival_at`, `missed_at`, and cancellation fields independently. An elapsed start time alone gives no evidence of a missed appointment. In history mode, `state=unstarted` excludes appointments with a linked consultation, so accepted cancellations can still appear. Use the returned `time_zone` to display appointments and honor the confirm and cancel eligibility flags.

### Read individual vital-sign captures

Use `/vital_signs` or consultation detail for the merged summary. Use these histories when you need each saved capture.

| Scope | Path after `/patient_portal` |
| --- | --- |
| Patient, including standalone captures | `/people/{person_id}/vital_signs_history` |
| One encounter | `/people/{person_id}/vital_signs_history?encounter_id={encounter_id}` |
| One clinical visit | `/consultations/{id}/vital_signs_history` |

Both history endpoints require a patient portal token and the organization’s clinical-sharing grant. Missing or invalid authentication returns HTTP 401. Disabled sharing returns HTTP 403. Inaccessible patients, visits, or encounter filters return HTTP 404. An accessible visit without captures returns an empty `vital_signs_history` array.

The `meta` object includes `page`, `per_page`, and `total_pages`. Page size defaults to 20 and is capped at 50. Pagination counts captures, so one encounter can span pages. Results sort by `recorded_at` descending with missing dates last and then by capture ID descending. An out-of-range page returns an empty array. `total_pages: 0` means the query found zero eligible captures.

Use the capture’s stable `id`. Group by its nullable `encounter_id` or `consultation_id` when useful and keep standalone captures visible. `recorded_at` is the saved creation timestamp, which can be supplied when the capture is created. `updated_at` is the last saved modification. `clinician` identifies the account attributed to the capture.

Render measurements by `key` to support historical and custom fields. Each capture contains its own populated values, including zero and false. Labels and units can be null. Current saved values take precedence, including explicit clears. A value found only in a snapshot appears when its saved timestamp is at least as recent as the capture.

### Handle clinical sharing

Medical history, vital signs, lab tests, and prescriptions return HTTP 403 when the patient’s organization has disabled medical-history sharing. With sharing enabled, `/medical_history` returns free-text allergies in `records.allergies` and catalogue entries in `medical_history_allergies`.

<Note>
  Reading `/medical_history` creates a record if no active history exists. Fetch it when the patient opens the medical history view.
</Note>

See the [patient portal specification](/openapi/nimbo_patient_portal.yml) for request parameters, response fields, and errors.
