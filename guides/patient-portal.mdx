Use the **Patient portal** reference to build a patient-facing integration. Its
patient session token is separate from the credentials used by the general
integration API.

## Authenticate the patient

1. Request a one-time code with `POST /api/v1/patient_portal/auth`, supplying
   `country_code` and `phone`.
2. Submit the received `code` with the same phone fields to
   `POST /api/v1/patient_portal/validate`.
3. Read `token` from the successful response. Send it as a bearer token on
   protected patient portal requests:

```http
Authorization: Bearer <PATIENT_PORTAL_TOKEN>
```

Use the API host provided for your integration. Never put tokens or received
codes in URLs, logs, analytics, or shared examples.

## Select an authorized patient

Call `GET /api/v1/patient_portal/people` to list the people available to the
session. Use an ID returned by that operation as `person_id` for subsequent
requests. A patient token does not grant access to arbitrary patient IDs.

## Read records and appointments

The reference includes consultations, prescriptions, lab results, vital signs,
shared attachments, medical history, appointments, consultation requests, and
available organization portals. Review each response root and pagination
parameters; these differ by operation.

<Note>
  The medical-history read creates a history record when the authorized patient
  has no active history. It is not a suitable request for a read-only health check.
</Note>

Handle authentication failures and unavailable resources using each operation's
response definitions. Reauthenticate when the session is no longer valid; do
not replace the patient token with an integration credential.

Download the [patient portal OpenAPI specification](/openapi/nimbo_patient_portal.yml).
